# PaperInfo 项目主要功能总结与介绍

> 面向项目讲解、内部分享与演示使用
> 文档依据：当前仓库代码实现（2026-07-24）

## 1. 一句话认识 PaperInfo

PaperInfo 是一套面向科研人员的本地论文情报与阅读管理工具。它围绕用户关心的研究领域，自动从 arXiv 和 DBLP 获取论文，借助大语言模型完成相关性与学术价值评估，再通过检索、翻译、收藏、统计、PDF 下载和 Zotero 导出等能力，把分散的论文发现过程整理为一条持续运行的工作流。

如果用一句更口语化的话来介绍：

> PaperInfo 像一位常驻本机的“论文助理”：它每天替你找论文、做第一轮筛选、整理元数据，并把值得阅读的内容送到你熟悉的阅读与文献管理环节。

## 2. 项目要解决的核心问题

日常论文调研通常存在几个反复出现的痛点：

1. **信息源分散**：预印本、会议和期刊论文分布在不同平台，需要分别检索。
2. **检索噪声较多**：只依赖关键词很容易得到“提到了关键词，但并不真正相关”的论文。
3. **持续跟踪成本高**：同一组检索条件需要周期性重复执行，电脑关机后还可能错过更新。
4. **阅读链路割裂**：发现论文之后，还要手工翻译、下载 PDF、整理引文并录入 Zotero。
5. **过程缺少记录**：很难快速回答“这次更新增加了什么”“哪些领域最近更活跃”“我之前看过什么”。

PaperInfo 的思路不是增加一个新的论文搜索框，而是把上述环节串成可以长期运行、可追踪、可配置的本地系统。

## 3. 从“发现”到“沉淀”的完整工作流

```text
研究领域配置
    ↓
arXiv / DBLP 自动抓取
    ↓
时间、分类、会场与关键词初筛
    ↓
去重 + LLM 双维度评分与过滤
    ↓
SQLite 持久化 + 元数据异步补全
    ↓
搜索 / 筛选 / 排序 / 翻译 / 收藏
    ↓
PDF、CSV、Excel、BibTeX、Zotero
    ↓
统计、阅读历史、更新日志与飞书通知
```

这条链路可以分成四个阶段来理解。

### 3.1 定义关注方向

系统以“研究领域”作为信息组织和抓取任务的基本单位。每个领域可以单独配置：

- 领域名称；
- 检索关键词；
- arXiv 分类；
- DBLP 会议或期刊；
- 是否启用；
- 领域专属的 LLM 评估提示词。

项目首次运行时会预置“区块链智能合约”和“大模型与自动化修复”两个方向。用户也可以直接在网页中新增、编辑或删除领域，而不必修改代码。

这套设计的价值在于：同一篇论文是否值得关注，往往取决于具体研究问题。领域专属提示词让筛选标准不再停留在通用关键词匹配，而可以表达更细的研究目标。

### 3.2 自动发现并筛选论文

PaperInfo 当前接入两类互补数据源：

- **arXiv**：适合跟踪最新预印本。系统按关键词批量查询，并结合 arXiv 分类和时间窗口提高精度。
- **DBLP**：适合跟踪目标会议与期刊。系统读取稳定的 venue stream，在本地按年份和标题关键词过滤。

抓取结果进入数据库前，还会经过多层处理：

1. 数据源内部的时间、分类、会场和关键词筛选；
2. 按来源与标题进行数据库去重；
3. 使用 LLM 分别给出“相关性”和“学术价值”两个 0～100 分的评分；
4. 两个分数都达到阈值的论文才会保存；
5. 对合格论文分批提交，降低单次事务失败的影响。

LLM 评估支持并行执行，也支持为不同领域使用不同提示词。在自定义双服务配置下，可由 GLM 作为主服务、DeepSeek 作为备用服务；主服务异常后会自动降级，并在冷却时间内避免反复请求故障服务。

需要注意的是：没有摘要的论文会跳过 LLM 内容评估并直接通过，等待后续元数据补全。因此，评分应理解为“辅助初筛信号”，而不是论文质量的最终结论。

### 3.3 在网页中完成浏览与阅读准备

主页是日常使用的核心入口，围绕“快速缩小候选范围”提供了：

- 按研究领域、数据源、年份、最近天数和更新批次筛选；
- 在标题、摘要和会议名称中搜索；
- 按发布日期、标题、相关性分或价值分排序；
- 分页浏览，以及按当前筛选条件跨页全选；
- 显示标题、作者、作者单位、摘要、来源、会场、日期和双维度评分；
- 跳转原始页面或直接访问 PDF；
- 对标题、摘要或整篇卡片执行中英翻译；
- 单篇或批量收藏、取消收藏和删除。

翻译服务采用 **Azure Translator → DeepSeek → MyMemory** 的自动降级链路，并内置常见学术术语表与译后修正。已翻译内容缓存在浏览器 `localStorage` 中，刷新页面后可以恢复，也可以再次点击在原文和译文之间切换。

网页还提供三个辅助视图：

- **收藏页**：集中整理用户明确标记的重要论文，并支持继续翻译和批量导出；
- **历史页**：分别查看最近抓取的论文和最近点击阅读的论文，点击次数会累计记录；
- **统计页**：展示论文总量、来源构成、年度与月度趋势、评分分布、收藏数量及各领域明细。

### 3.4 把论文沉淀到后续工作流

对于筛选后的论文，系统支持按勾选结果、全部收藏或当前筛选条件跨页批量导出：

- **CSV**：适合轻量数据交换；
- **Excel（XLSX）**：带基础列宽和冻结表头，便于直接查看和二次整理；
- **BibTeX**：用于 LaTeX 写作和引文管理；
- **PDF / ZIP**：单篇直接下载 PDF，多篇自动打包；
- **本地 Zotero**：选择当前 Zotero 资料库或分类，写入结构化元数据，并尝试附加全文 PDF。

Zotero 集成通过本机 Connector 接口完成，不依赖 Zotero 云端 API Key。论文会被映射为预印本或会议论文条目，并携带作者、摘要、DOI、来源、领域标签和作者单位等信息。

## 4. 元数据补全：让“只有题录”逐步变成“可阅读记录”

不同数据源提供的元数据完整程度并不一致，尤其是 DBLP 记录可能缺少摘要、作者单位或可直接下载的 PDF。PaperInfo 因此提供了独立的异步补全流程。

新论文保存后，系统会在后台尝试补全：

- 作者及其所属机构；
- DOI；
- 摘要；
- 公开可访问的 PDF 地址。

补全链路综合使用 OpenAlex、Unpaywall、Crossref、arXiv 元数据和出版商页面，并对 PDF 地址进行可用性验证。任务在后台限速运行，不阻塞主抓取流程；暂时缺失的摘要或 PDF 还会按照约 1 天、3 天、7 天和 30 天的节奏延迟重试。

用户也可以从界面手动启动历史论文的元数据回填，并查看任务进度。这样，系统能够先快速完成“发现和入库”，再逐步提升记录的可读性和可用性。

## 5. 自动运行、通知与可追踪性

PaperInfo 同时支持手动更新和定时更新。默认调度器使用 Asia/Shanghai 时区，每天在配置时间执行抓取。

为了适应个人电脑的使用场景，系统实现了“错过任务补执行”：

- 应用启动后会检查当天计划是否已经完成；
- 每 5 分钟再次检查一次；
- 如果电脑在计划时间关机，重新启动服务后可以补抓；
- 正常任务开始后的保护窗口内不会误触发重复补执行。

系统还通过线程锁与进程级文件锁阻止多个更新任务同时运行，避免重复抓取和数据库竞争。arXiv 请求具有重试与熔断机制；DBLP 则支持多个官方镜像、条件请求、本地缓存和旧缓存兜底。某个来源整轮不可用时，任务会明确标记为“部分成功”，而不是把其他来源的有效结果一并判为失败。

每次定时、手动或补执行更新都会生成日志，记录：

- 触发方式与时间；
- 新增论文数量；
- 各数据源新增数量；
- LLM 过滤数量；
- 处理领域；
- 任务耗时；
- 成功、部分成功或失败状态；
- 数据源异常和错误信息。

配置飞书群机器人后，系统会自动推送更新卡片，包括执行摘要、来源异常以及最多 5 篇优先论文。通知失败不会反向影响抓取和入库。

## 6. 主要页面与能力速览

| 页面或模块 | 主要作用 | 典型使用场景 |
| --- | --- | --- |
| 论文主页 | 搜索、组合筛选、排序、翻译、批量操作 | 每天查看新论文并完成第一轮筛选 |
| 领域管理 | 配置关键词、分类、会场和 LLM Prompt | 新增研究方向或调整筛选标准 |
| 收藏页 | 汇总重点论文并批量导出 | 建立待读清单、准备文献综述 |
| 历史页 | 查看最近抓取与最近点击 | 找回刚看过或最近入库的论文 |
| 统计页 | 观察来源、年份、月份、评分和领域分布 | 了解资料库结构与研究方向活跃度 |
| 更新日志 | 查看每次任务结果和异常 | 排查某次更新为什么没有新增论文 |
| 元数据补全 | 回填单位、摘要与 PDF | 改善历史 DBLP 记录的完整度 |
| 导出与 Zotero | 输出表格、引文、PDF 或写入文献库 | 从“发现论文”进入阅读和写作阶段 |

## 7. 技术架构概览

项目采用单体、本地优先的架构，部署和维护成本较低：

- **Web 层**：Flask + Jinja2 + Bootstrap；
- **数据层**：Flask-SQLAlchemy + SQLite；
- **调度层**：APScheduler；
- **采集层**：arXiv Atom API 与 DBLP venue stream；
- **智能处理层**：可配置 LLM 评估器与多级翻译服务；
- **元数据层**：OpenAlex、Unpaywall、Crossref、arXiv 与出版商页面；
- **集成层**：本地 Zotero Connector、飞书自定义机器人；
- **运行方式**：前台开发运行，或通过 Windows 任务计划程序后台自启动。

核心代码职责大致如下：

| 文件或目录 | 职责 |
| --- | --- |
| `app.py` | 应用初始化、页面路由和 API |
| `models.py` | 研究领域、论文、更新日志和阅读历史模型 |
| `crawler/` | arXiv 与 DBLP 抓取、限速、重试、缓存和标准化 |
| `scheduler.py` | 定时任务、补执行、抓取编排、LLM 筛选和日志 |
| `llm/` | 多提供商评分及主备服务降级 |
| `affiliation_service.py` | 作者单位、摘要和 PDF 元数据补全 |
| `translation_service.py` | 学术文本翻译与服务降级 |
| `pdf_service.py` | PDF 校验、下载与 ZIP 打包 |
| `zotero_service.py` | 本地 Zotero 条目及附件写入 |
| `notification_service.py` | 飞书更新通知 |
| `templates/`、`static/` | 页面展示与浏览器交互 |

## 8. 适合分享时强调的项目亮点

### 8.1 它是一条工作流，而不只是一个爬虫

项目的价值不只在于“抓到了多少篇”，更在于覆盖了论文发现、筛选、阅读准备、收藏和沉淀的连续过程，减少了平台之间的手工搬运。

### 8.2 规则筛选与模型判断分层协作

分类、会场、时间和关键词负责低成本缩小候选集，LLM 再判断论文与具体研究问题的相关程度和潜在价值。两类方法各自处理擅长的问题，也便于控制调用成本。

### 8.3 对个人电脑运行环境做了实际适配

定时任务补执行、后台自启动、并发锁、日志、来源熔断和缓存兜底，解决的都是“工具长期放在个人电脑上运行”时真实会遇到的问题。

### 8.4 把外部服务故障当作正常情况处理

LLM、翻译、DBLP 镜像、元数据源和通知均采用不同程度的降级或隔离设计。单个服务失败时，系统尽量保留其他环节已经完成的结果。

### 8.5 本地优先，数据掌握在用户手中

论文库使用本地 SQLite 保存，Zotero 通过本地接口连接，用户可以直接备份数据库、导出资料，也能清楚知道每次更新做了什么。

## 9. 一个适合现场讲解的演示顺序

如果要在 5～10 分钟内介绍项目，可以按下面的顺序演示：

1. **打开主页**：先展示论文卡片、双评分和筛选栏，说明系统最终交付的是可阅读的候选论文。
2. **打开领域管理**：展示关键词、arXiv 分类、DBLP 会场和领域 Prompt，说明论文是围绕研究问题持续跟踪的。
3. **触发单领域更新**：介绍 arXiv/DBLP 抓取、去重、LLM 筛选和更新日志。
4. **翻译并收藏一篇论文**：展示从英文题录到中文快速判断的过程。
5. **跨页全选并导出**：选择 BibTeX、PDF 或 Zotero，体现与后续阅读和写作工作流的衔接。
6. **查看统计与更新日志**：用数据说明系统如何记录长期积累和运行状态。
7. **补充自动化能力**：最后说明每日定时更新、关机后的补执行、飞书通知和后台自启动。

这个演示顺序先让观众看到结果，再解释结果如何产生，最后展示系统如何长期运行，理解成本相对较低。

## 10. 当前边界与使用提醒

- 当前主数据源是 arXiv 和 DBLP，覆盖范围受领域关键词、分类、venue 映射和时间窗口影响。
- LLM 分数适合排序和初筛，不应替代研究者对方法、实验和结论的判断。
- DBLP 论文若暂时没有摘要，会直接入库并等待后台补全，因此初始评分可能为空或采用直通分。
- 翻译缓存保存在当前浏览器本地，不是数据库级、跨设备同步的译文库。
- PDF 下载与 Zotero 附件保存依赖论文是否存在公开且可访问的 PDF。
- Zotero 导出要求本机 Zotero 桌面端正在运行。
- OpenAlex、Unpaywall、付费 LLM、Azure 翻译和飞书通知等能力需要相应配置；未配置时，系统会跳过或使用可用的后备链路。
- 项目目前更适合个人或小团队在可信网络中使用。如需公开部署，还应补充登录鉴权、权限控制、密钥治理、备份和生产级 Web 服务配置。

## 11. 总结

PaperInfo 的核心定位可以概括为：

> 以研究领域为中心，以自动抓取为入口，以 LLM 辅助筛选为中间层，以阅读、收藏和导出为落点的本地论文情报工作台。

它把科研信息获取中大量重复、分散的操作集中到一个系统中，同时保留研究者对领域定义、筛选标准和最终判断的控制权。对于需要长期跟踪若干明确研究方向的用户，这种“自动发现 + 人机协同筛选 + 本地沉淀”的方式，比一次性的网页检索更适合形成持续、可复用的调研流程。
